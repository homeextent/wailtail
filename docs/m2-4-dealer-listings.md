## Bounded application-to-listing flow

Consignment Pipeline → View application → Approve dealer vehicle and create draft is separate from Manage dealer verification. Only canonical `consignment_applications` dealer applications are eligible. The administrator records a vehicle approval reason, explicitly confirms curation approval and chooses an informational tax arrangement (default: requires confirmation). Reading eligibility and viewing forms make no writes.

The trusted `admin-dealer-listing` endpoint requires revocation-checked, email-verified designated administrator identity and strict input allowlists. It resolves the private M2.3 case/profile, verifies the current representative in Firebase Auth, and transactionally checks current verification, expiry, both protected account links, current case revision and the inspected application's fingerprint. Changed application data requires a reload. The representative UID never comes from the applicant email or browser payload. Auth checks precede the Firestore transaction; these services cannot share one atomic transaction.

Conversion requires pending/reviewed/approved status with no prior conversion, the current M2.2 declaration version, all three declarations and terms, and valid vehicle identity fields. A deterministic application-derived listing ID, revision checks and actor-bound command fingerprints prevent duplicate drafts and conflicting retries. One transaction creates the draft, media configuration, command record and immutable conversion audit, and sets the canonical application's approval/conversion reference. A rejected commit retains no partial approval, listing, media or audit. Legacy mirrors are unchanged; legacy/private one-click conversion remains disabled. Application notes and free-text reserve expectations are not promoted into narrative or trusted financial values. The administrator completes the vehicle draft in the editor.

## Attribution, commercial fields and access

- The server sets `sellerType: dealer`, protected dealerId, exact representative sellerId, source-application provenance, `dealerDocFee: 0`, CAD currency, taxHandling and the server's taxDisclaimerVersion. Existing configured starting-bid/increment defaults are respected. No tax calculations, tax collection, payments or account-role promotion are added.
- The creation-time dealerSnapshot is a strict allowlist: canonical business/display/DBA name, city/province, verification timestamp/revision and only opted-in business phone/website. It excludes street/postal address, licence/jurisdiction, representative email/phone, findings and private evidence. It remains internal in M2.4: the public auction projection does not expose the snapshot or provenance. M2.5 owns badges, public disclosures, contact/consent presentation and marketing.
- Snapshot/ownership reassignment and refresh are unavailable. Later profile changes do not rewrite existing listing history. Dealer duplication is rejected; new inventory requires a separately reviewed canonical application. Generic listing updates cannot change protected dealer, fee, tax or ownership fields; dealer seller display name and CAD currency remain protected.
- The admin editor displays a protected attribution summary and a separate draft-only tax-indicator control with reason, revision/idempotency protection and an audit. Requires confirmation blocks forward publication. Current verification, expiry and protected account links are checked before a draft/pending-review dealer listing enters preview/upcoming/active/live/ending-soon visibility, including bulk status changes; failure rejects the full transaction. Existing visible/historical lots and settlement are not automatically rewritten or interrupted by later suspension/expiry.
- Assigned representatives use the existing restricted narrative/media workspace at `/dashboard/listings/[id]/edit`. Access is enforced by authenticated UID ownership, not a global seller role. The account hub lists only server-selected owned lots, and dealer-linked members can reach My Listings without a role promotion. Narrative, media and submission retain M2.3 eligibility guards, optimistic seller revisions and pending-review locking. Protected identity, commercial data and snapshots are outside seller payloads. Ineligible dealer drafts remain inspectable but read-only.
- Approved dealer applications are excluded from email-based consignor role authorization, revalidated inside its transaction; that flow cannot rebind dealer auctions. Existing private-seller authorization remains separate and covered by regression tests.

## Persistence and boundaries

`dealerListingCommands/{hash}` is server-only retry metadata. `dealerListingAudits/{hash}` is private designated-admin-readable, with all client writes denied and trusted endpoint create-only audit records. Events record actor UID/email, reason, time, source/target, relevant before/after and verification provenance. Source application approval fields retain the existing applicant-readable schema; private audit data is separate. Cloud administrators with privileged credentials inherently bypass client rules.

Source rules must be separately approved and published before operational rollout; Vercel does not publish Firebase rules. No production data or Storage work is authorized here. No legacy adoption, dealer reassignment, multiple representatives, automatic listing publication, scheduling changes, public dealer presentation, registry automation, email delivery or bidding/settlement redesign is included. Existing Storage/Firestore cross-service upload interruption limits remain unchanged.
